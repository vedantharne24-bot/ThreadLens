## C. Monitoring overhead (stress workload)

`stress T 20000 16 30 200`: each thread performs 20000 lock operations on 16 mutexes (30 % nested, ~200 ns of work inside). Time is the program's own CLOCK_MONOTONIC measurement around the worker phase (median of repetitions).

* **baseline** – no collector; **passive** – collector preloaded, no output configured (interposition cost only);
* **trace** – collector writing a binary trace file; **live** – full pipeline: collector → Unix socket → backend analysis + SQLite.

| 8 | 96.6 ms | 101.3 ms (1.05×) | 185.1 ms (1.92×) | 5383.7 ms (55.71×) | 615330 | 103723 |

Overhead depends strongly on how often the program calls into pthreads: this workload is lock-bound by design (worst case). Programs that do real work between lock operations see much less.

* **passive** shows that interposition itself is close to free (≈1.0×).
* **trace** (≈2×) is the cost of producing and writing every record.
* **live** is bounded by the backend's measured ingest rate (last column): with the default 100 ms back-pressure budget the program is slowed to the rate at which the Python analyzer consumes events, so that no event is lost. With `block_us=0` the program is not slowed but events are dropped (section D) and the verdict becomes inconclusive.

Whenever events are lost the verdict is downgraded to *inconclusive* instead of reporting a possibly wrong result.

Probe effect: with full back-pressure a thread can be delayed inside the collector while it holds a lock, which lengthens hold times and the waits of other threads. The *excessive contention* verdict for the stress program under live monitoring is therefore partly caused by monitoring itself (its ground truth accepts this; the program has no deadlock or lock-order cycle, and none was reported).

Note on the Helgrind *errors* column for hanging programs: in those runs Helgrind's only messages were "Exiting thread still holds 1 lock", printed when the scenario's watchdog terminated the hung process. They are a side effect of the forced termination, not a deadlock diagnosis: no lock-order report was produced, because the second lock acquisitions never complete.

Interpretation: TSan and Helgrind predict lock-order inversions from completed acquisitions (and find data races, which ThreadLens does not attempt); Helgrind also reports pthread API misuse well. A program that actually deadlocks simply hangs under them until a timeout; ThreadLens confirms the hang as a wait-for cycle with evidence within milliseconds. The tools are complementary.
